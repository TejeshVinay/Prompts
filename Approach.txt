# SCP Alert Intelligence / Triage System — Implementation Plan

**Status:** Draft v1
**Source of truth:** The project specification pasted by the author. Where this plan
adds judgement beyond that source, the section is marked **[PLAN NOTE]**.
**Scope:** Turn existing work (feature engineering + four trained unsupervised models)
into a coherent, auditable pipeline ending in a supervisor-facing explanation.

---

## 0. Framing

### 0.1 What this system claims

The ML layer identifies **behavioural unusualness relative to the historical alert
population**. It does not claim:

- anomaly = risk
- anomaly = misconduct
- anomaly = non-BAU

The final decision remains with the supervisor.

### 0.2 The seven questions the system must answer

For any alert:

1. How anomalous is this alert according to each model?
2. Do the different models agree?
3. What is the unified/consensus anomaly score?
4. Which features contributed to the anomalous result?
5. What related alerts belong to the same episode?
6. What contextual relationships exist in the graph?
7. Can GraphRAG combine these into a useful explanation for a supervisor?

### 0.3 Separation of responsibilities (non-negotiable)

| Layer | Question it answers | What it must NOT do |
|---|---|---|
| Episodic linking | Which alerts are related? | Use anomaly scores or outcome labels to form episodes |
| ML models | How behaviourally unusual is this alert? | Operate on leaked post-review fields |
| Consensus | Do multiple detectors agree on unusualness? | Hide model disagreement |
| XAI | Which features contributed to the model output? | Claim causality |
| GraphDB | How are alerts, episodes and entities connected? | Contain invented relationships |
| GraphRAG | What contextual evidence can we retrieve? | Act as the anomaly detector |
| LLM | How do we present retrieved evidence? | Invent scores, features, relationships or episode membership |

### 0.4 Scoring unit

The primary scoring unit is the **alert**, not the episode. An episode may contain
normal alerts, anomalous alerts, or both. Episode-level anomaly scores must **not** be
produced by averaging member alert scores. The episode supplies context around the
alert.

**[PLAN NOTE]** An episode-level signal is still useful, but it must be a separately
defined and separately justified quantity (e.g. count and share of member alerts in the
Top 5% band, episode cohesion, episode duration vs. historical episodes of the same
type). Treat it as descriptive context, not as a second anomaly model, unless and until
it is explicitly designed as one.

## 1. Target architecture

```
ALERT DATA
    -> EPISODIC LINKING            -> episode_id
    -> FEATURE ENGINEERING         -> FEATURE AUDIT -> validated feature set
    -> IF | LOF | AE | OCSVM       -> raw model scores
    -> SCORE DIRECTION FIX
    -> PERCENTILE NORMALIZATION    -> common 0-100 scale
    -> CONSENSUS ANOMALY SCORE     -> model agreement + alert ranking
    -> MODEL-SPECIFIC XAI          -> feature evidence
    -> GRAPHDB                     -> Alert | Episode | Entities
    -> GRAPHRAG                    -> contextual explanation
    -> SCP ASSISTANT               -> SUPERVISOR
```

### PHASE 2 — Feature engineering audit and validation

**Objective:** Establish that the feature matrix represents **behaviour available at the
time the alert was generated**. The objective is not to maximise feature count.

**2.1 Per-feature validation table**

Produce one row per feature:

```
feature
feature_type
source_column(s)
calculation
missing_percentage
unique_count
variance
range
outlier_percentage
distribution_summary
prediction_time_available
possible_leakage
redundancy/correlation
model_compatibility
recommendation        # KEEP | MODIFY | REMOVE | INVESTIGATE
rationale
```

No feature is removed automatically. Every KEEP and every REMOVE carries a written
reason.

**2.2 Fields requiring particular scrutiny**

These may be valuable for analysis or for GraphDB, but must not silently become ML
features:

- alert IDs, trade IDs, account IDs, supervisor IDs, rule IDs, episode IDs
- timestamps
- post-review fields
- sign-off fields
- RFI fields
- supervisor comments
- closure status
- any field created after the alert was generated

**[PLAN NOTE] Routing confound.** Supervisors have hierarchy and specialisation, so
alert routing is imbalanced and supervisor identity correlates with alert type. If
supervisor or GPN is used as a model feature, the models can learn "alerts routed here
are unusual", which is a property of the org chart rather than of behaviour. Default
position: supervisor and GPN are **linking keys and graph nodes, not model features**.
If they are retained as features, the audit must state why.

**2.3 Redundancy and correlation analysis**

Perform:

- Pearson correlation where appropriate
- Spearman correlation where appropriate
- categorical association where appropriate
- near-zero variance analysis
- duplicate/redundant feature analysis

For each strongly correlated group, answer:

1. Which features are strongly correlated?
2. Do they represent genuinely different business concepts?
3. Could simultaneous use overweight a particular behaviour?
4. Is dimensionality reduction or selective removal justified?

Correlated features are **not** removed blindly — anomaly models can benefit from
multiple related behavioural signals.

**2.4 Distribution artefacts**

Generate: histograms/distributions, boxplots where useful, correlation matrix,
missingness summary, feature variance summary.

**2.5 Alert-level vs episode-level features**

Maintain an explicit split:

- **Alert-level features** — derived from the alert itself.
- **Episode-level features** — e.g. `episode_alert_count`, `episode_duration`, number of
  related alerts, activity frequency within episode, distinct entity count, temporal
  density, operation/action count, historical episode characteristics.

**2.6 Temporal leakage rule**

If Alert A occurs at T1 and Alert B at T2 > T1, features for Alert A must not use
information from B. Every episode-derived feature must be computable from data known at
the alert's own timestamp.

Label every feature as either:

- **REAL-TIME AVAILABLE** — usable in the production scoring path
- **RETROSPECTIVE ONLY** — usable for analysis and reporting, not for scoring

**[PLAN NOTE]** Most naive episode features (`episode_alert_count`, `episode_duration`)
are retrospective by construction, because the episode is not complete when its first
alert arrives. The fix is to define them as-of the alert timestamp — e.g. "number of
prior linked alerts in the 30 days before this alert" rather than "size of the episode
this alert ended up in". Expect to rewrite several features here.

**Deliverables:** Feature Engineering Validation Report; validated feature matrix;
real-time vs retrospective feature register.

**Exit criterion:** Every feature carries a recommendation and a leakage verdict, and
the feature matrix used for scoring contains no RETROSPECTIVE ONLY feature.

### PHASE 3 — Audit the four models and their scoring functions

**Objective:** Know exactly what each trained model outputs before consuming it.

The four models and their definitions of unusualness:

| Model | Definition of unusualness |
|---|---|
| Isolation Forest | Isolates observations through recursive/random partitioning |
| Local Outlier Factor | Evaluates local density relative to neighbouring observations |
| Autoencoder | Reconstructs normal patterns; reconstruction error is the signal |
| One-Class SVM | Learns a boundary around the distribution; outside = anomalous |

For each model record:

- raw score and its exact scoring function
- score direction (does higher or lower mean more anomalous?)
- score distribution and range
- required preprocessing (scaling, encoding) and whether it matches Phase 2 output

**Critical fact:** raw scores across these four models are **not directly comparable**.
Nothing downstream may compare or combine raw scores.

**Exit criterion:** A signed-off table of the four scoring functions and directions.

---

### PHASE 4 — Generate raw scores for all alerts

Run all four models over the validated feature matrix. Persist raw scores alongside
`alert_id`. No transformation at this stage.

**Deliverable:** Raw Model Score Table.

---

### PHASE 5 — Common score representation

**Objective:** Put all four models on one anomaly-oriented scale. This is one of the
most important parts of the implementation.

Per model:

```
raw model score
    -> correct score direction (so that higher = more anomalous)
    -> rank / percentile
    -> 0-100 anomaly scale
```

Interpretation:

- `0` = relatively normal compared with the evaluated population
- `100` = relatively highly anomalous compared with the evaluated population

This is **not a probability**.

Example (normalized percentiles, not raw scores):

```
Alert A:  IF = 97   LOF = 94   AE = 96   OCSVM = 92
```

**[PLAN NOTE]** Percentile normalisation is relative to the evaluated population, so the
score answers "how unusual is this alert compared to this batch" rather than "how
unusual in absolute terms". Two consequences to document and decide:

1. Fix the reference population explicitly (full historical corpus vs. rolling window
   vs. per-event-type cohort). Scores are not comparable across different reference
   populations.
2. For production scoring of new alerts, freeze the percentile mapping from a reference
   run rather than recomputing ranks per batch, otherwise yesterday's 95th percentile is
   not today's.

**Deliverable:** Normalized Model Score Table.

---

### PHASE 6 — Consensus score and model agreement

```
consensus_anomaly_score = mean(IF_pct, LOF_pct, AE_pct, OCSVM_pct)

model_agreement = standard deviation of the four normalized scores
                  (low sd  = models agree
                   high sd = models disagree)
```

Model disagreement must **not** be hidden.

Worked examples:

```
Alert A:  IF 97  LOF 95  AE 96  OCSVM 94
          consensus = 95.5   agreement = high   (strong multi-model evidence)

Alert B:  IF 98  LOF 51  AE 47  OCSVM 55
          consensus = 62.75  agreement = low    (models see this differently)
```

**Deliverables:** Consensus Anomaly Score Table; Model Agreement Analysis.

---

### PHASE 7 — Model comparison

Calculate:

- Spearman rank correlation between models
- Pearson correlation where meaningful
- Top 1% / Top 5% / Top 10% overlap
- intersection of all four models
- pairwise overlap

**Deliverable:** Model Comparison Report answering "Are the four models identifying
similar anomalous observations?" and "Where do they disagree?".

**[PLAN NOTE]** This phase is also the evidence base for whether four models are
warranted. If two models correlate above ~0.95 in rank and their top-K sets largely
coincide, they are contributing one signal at twice the explanation cost. Record the
finding; decide on model count after seeing it, not before.

---

### PHASE 8 — Ranking and banding (no forced binary label)

Do **not** create an arbitrary `anomaly = score > 0.5`.

Emit instead:

- `consensus_anomaly_score`
- `global_rank`
- `percentile`
- `percentile_band` ∈ {Top 1%, Top 5%, Top 10%, Normal range}

A hard operational threshold is introduced only after the score distribution and its
business meaning are understood.

**Master alert-level output table:**

```
alert_id
episode_id
IF_raw_score,     IF_anomaly_percentile
LOF_raw_score,    LOF_anomaly_percentile
AE_raw_score,     AE_anomaly_percentile
OCSVM_raw_score,  OCSVM_anomaly_percentile
consensus_anomaly_score
model_agreement
global_rank
percentile_band
<validated feature set>
```

### PHASE 9 — Model-specific XAI

XAI has two separate purposes that must not be mixed:

- **A. Model XAI** — "Why did the model consider this alert anomalous?"
- **B. Graph/episode context** — "What is happening around this alert?"

This phase covers A only.

**9A. Isolation Forest — feature attribution (SHAP where technically appropriate)**

Per selected high-anomaly alert, emit: `feature`, `feature_value`, `contribution`,
`direction`. Rank by contribution.

**9B. Autoencoder — reconstruction-error explanation**

Per selected alert, emit: `original_value`, `reconstructed_value`, `absolute_error`,
`squared_error`, `contribution_percentage`. Rank features by contribution to total
reconstruction error.

**This is not SHAP and must not be labelled SHAP.**

**9C. LOF — local perturbation / sensitivity explanation**

LOF is a local-density algorithm and has no native tree-style attribution. Procedure:

1. Calculate original LOF score.
2. Perturb one feature at a time toward a valid reference value.
3. Recalculate the anomaly score.
4. Measure the change.
5. Rank features by score impact.

Label the output explicitly as **"local perturbation-based explanation"**, not a causal
explanation.

**9D. One-Class SVM**

Use an explanation method valid for the trained implementation. Where SHAP is
technically valid, use it; otherwise use a model-agnostic local perturbation/sensitivity
approach. Do not copy the Isolation Forest method across by assumption.

**9E. Unified explanation object**

Per selected high-anomaly alert:

```
Alert:                    A102
Consensus anomaly score:  95.4
Model agreement:          High
Model evidence:
    Isolation Forest   97 percentile
    LOF                94 percentile
    Autoencoder        96 percentile
    One-Class SVM      95 percentile
Top contributing behavioural features:
    feature_1, feature_2, feature_3
Model-specific evidence:
    <per-model detail as above>
```

It must answer: how anomalous is the alert; do the models agree; which behavioural
features contributed; which models give the strongest evidence; is the anomaly driven by
one model or several.

**[PLAN NOTE]** The top-contributing-features line is a summary across four differently
derived attributions, which are not on a common scale. Define the aggregation rule
explicitly (e.g. rank-vote across models, or attribute only from the highest-scoring
model) and state the rule in the supervisor-facing output. Do not average raw
attribution magnitudes across methods.

**9F. Counterfactual explanations**

Question answered: *"What minimal feature changes would move this observation toward the
learned normal region?"*

Not: "What should the trader have done?" Not: "This caused the suspicious behaviour."

Required phrasing: *"According to the model, moving feature X toward the learned normal
range would reduce the anomaly score."*

Respect valid ranges, non-negative constraints, categorical constraints, and
business-valid feature combinations. Generate for **selected alerts only**, not all 50K.

**Deliverables:** Model-specific XAI results; counterfactual explanations for selected
alerts.

### PHASE 10 — Episodic context integration

Episodic linking is **not** an anomaly detector. Its purpose is to determine which alerts
belong to the same underlying business/activity lifecycle.

Illustration of one episode:

```
Alert A -> Cancel
Alert B -> Amend
Alert C -> Cancel
Alert D -> Rebook
Alert E -> Amend
```

**Permitted linking signals only:**

- temporal proximity
- common entity/account
- common transaction/trade
- rule/type relationship
- operation/action relationship
- relevant attribute similarity

**Prohibited:** anomaly scores as linking input; ground-truth outcome labels as linking
input.

Use the existing implementation. If incomplete, audit before changing.

Preserve per alert: `alert_id`, `episode_id`, episode metadata.

**[PLAN NOTE] Unified linking score.** Where linking attributes are tiered
(strong/moderate/weak) and applied across multiple sections, produce **one** unified
weighted score rather than per-section episode sets, so an alert has a single
`episode_id`. Recommended refinements:

- Require at least one strong or moderate match before scoring; weak attributes alone
  must not create a link.
- Weight by match rarity rather than by hand, so a shared trade ID outweighs a shared
  supervisor.
- Block candidate pairs on strong keys before scoring, rather than scoring all pairs.
- Apply a time window or decay.
- Inspect the episode size distribution for chaining (A–B, B–C merging into one giant
  episode); tighten the join threshold or use community detection if present.

**[PLAN NOTE] Edge evidence schema.** Store on every alert–alert edge:
`matched_attributes`, `tier`, `weight`, `contribution`, `link_type`, `total_score`,
`threshold`. This is what makes episode formation explainable and preserves the
per-section distinction (lifecycle vs transactional) as edge metadata rather than as
separate graphs. Fix this schema before finalising the scoring weights — everything in
Phase 12's episode explanation depends on it.

**Deliverable:** Episode/Alert relationship table.

---

### PHASE 11 — GraphDB

GraphDB is a separate contextual layer. The ML models determine anomalousness; the graph
represents relationships. **Only create relationships supported by the dataset. Do not
invent graph facts.**

**Nodes:** Alert, Episode, Transaction/Trading Activity, Account/Entity, Rule, Operation,
Supervisor, other relevant business entities.

**Relationships:**

```
Alert       -PART_OF->          Episode
Alert       -RELATED_TO->       Alert
Alert       -TRIGGERED_BY->     Rule
Alert       -ASSOCIATED_WITH->  Entity
Episode     -CONTAINS->         Alert
Transaction -GENERATED->        Alert
```

**ML results exposed as node properties:**

```
Alert A102
    consensus_anomaly_score = 95.4
    model_agreement         = 0.91
    percentile_band         = Top 5%
    PART_OF    -> Episode E42
    RELATED_TO -> Alert A103, Alert A104
```

The graph must let us traverse:

```
ALERT -> ML SCORE -> XAI EVIDENCE -> EPISODE -> RELATED ALERTS -> ENTITIES / ACTIVITIES
```

**Deliverables:** GraphDB schema; populated GraphDB.

---

### PHASE 12 — Graph retrieval layer

Expose ML + XAI + episode information through graph retrieval before building the
conversational layer.

**[PLAN NOTE]** Implement retrieval as a fixed set of parameterised queries, not
free-form text-to-Cypher. Suggested starting set:

| Query | Returns |
|---|---|
| `alert_evidence(alert_id)` | Scores, agreement, band, XAI evidence |
| `episode_members(alert_id)` | Episode members with their own scores and bands |
| `link_evidence(alert_a, alert_b)` | Matched attributes, tier, contributions, link type, score vs threshold |
| `episode_formation(episode_id)` | Shared attributes, time span, cohesion, weakest link |
| `related_history(entity, window)` | Prior alerts for the entity, restricted to timestamps earlier than the current alert |

`related_history` must filter to **earlier** alerts only, so no future information
reaches a current alert's context.

**[PLAN NOTE] Episode-level explainability.** Alongside the anomaly explanation, expose a
separate grouping explanation at three levels: why two alerts are linked (edge
evidence); why this alert sits in this episode (strongest link, link count, and the
counterfactual "without attribute X this alert falls below threshold"); how the episode
formed (shared attributes, time span, cohesion, weakest bridging link). Add an
**episode confidence** value derived from cohesion, minimum edge strength and share of
strong evidence, and display it beside — never merged with — the anomaly score. These
answer different questions and must stay visually distinct in the supervisor UI.

---

### PHASE 13 — GraphRAG and supervisor-facing explanation

**Pipeline:**

```
Supervisor question
    -> question interpretation
    -> graph retrieval / Cypher
    -> relevant alert/episode/entity evidence
    -> retrieve ML score + XAI evidence
    -> context assembly
    -> LLM
    -> evidence-grounded response
```

**Worked retrievals:**

| Question | Retrieve |
|---|---|
| "Why is Alert A102 highly anomalous?" | A102; consensus score; four model scores; model agreement; XAI feature contributions; episode ID; related alerts; episode characteristics; connected entities |
| "Which alerts are related to A102?" | Graph relationships and episode membership |
| "What makes this episode unusual?" | Episode members; individual anomaly scores; anomalous alert count; episode features; related entities; temporal relationships |

**Hard constraint:** the LLM must not invent anomaly scores, feature values,
relationships, episode membership or model outputs. Every answer is grounded in
retrieved evidence. All explanation content is computed upstream and stored; the LLM
only renders it.

**Deliverables:** GraphRAG retrieval pipeline; example supervisor questions with grounded
answers; final supervisor-facing explanation format.

## 4. Terminology the final output must distinguish

| Term | Meaning |
|---|---|
| Anomaly score | One model's view of how unusual an alert is, on the 0–100 percentile scale |
| Consensus score | Mean of the four normalized percentiles |
| Model agreement | Standard deviation of the four normalized scores; low sd = agreement |
| XAI | Which features contributed to a model's anomalous output |
| Episodic linking | Which alerts belong to the same business/activity lifecycle |
| GraphDB | How alerts, episodes and entities are connected |
| GraphRAG | Retrieval of graph + ML + XAI evidence to answer a supervisor's question |

## 5. Acceptance test

The system is not accepted because the code runs. It is accepted when, for a given
alert, it can answer in one grounded response:

> Why did the system consider this particular alert unusual, how strongly do the four
> models agree, what features contributed to the result, what other alerts are related to
> it, what episode does it belong to, and what contextual evidence can we retrieve for
> the supervisor?

## 7. Standing rules

1. Do not skip the feature-engineering audit because features already exist.
2. Do not retrain models before understanding their current results.
3. Do not discard existing work because it is imperfect.
4. Do not use anomaly scores or outcome labels to create episodes.
5. Do not force a binary anomaly label early.
6. Do not average alert scores into an episode anomaly score.
7. Do not let the LLM or GraphRAG act as the anomaly detector.
8. Do not present anomaly as equivalent to risk, misconduct or non-BAU.
